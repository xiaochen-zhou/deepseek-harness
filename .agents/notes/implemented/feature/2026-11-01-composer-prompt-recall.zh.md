# Agent Note: 输入框用上下方向键取回已提交的提示

Status: implemented

[English](2026-11-01-composer-prompt-recall.md) | 中文

## 问题

输入框里已经发出去的内容只能重新输入。用户熟悉的其他终端式入口（shell 历史、Codex、Claude Code）按 ↑ 就能取回上一条提示，而一段长提示只想改几个字时，重打是最贵的操作。

## 决策

↑/↓ 遍历本会话已提交的提示，从最新往回走，把每一条写进草稿。

- `ComposerHistory`（`SessionInputDeps.history`）是这份记录：`entries()` 从旧到新，加上 `record(text)`；InputHub 为每个 Session 绑定持有一份。提交时追加，空白草稿和紧邻的重复提交不追加，所以连续发两次同样的内容不会在回溯里留下两个相同的停留点。
- 回溯状态由 `SessionInputShell.history(direction)` 拥有：游标、用户自己的草稿，以及回溯最后写入的文本。进入回溯要求草稿为空，因此在写了一半的提示里按 ↑ 仍然移动光标；从最新一条再往下按会恢复那份写了一半的草稿；不是回溯本身的编辑会终止回溯（`onEditorUpdate` 会把投影文本与回溯写入的文本比较）。
- 输入框的键盘映射先把方向键交给打开的菜单（`arbitrate`），再交给 `history()`，两者都不认领才落回光标移动。带修饰键的方向键（Shift/Alt/Meta/Ctrl）和输入法组字期间的按键不会进入回溯，选区扩展与候选词选择保持原生行为。
- 提交、以及输入框处于锁定/冻结状态时的按键都会结束回溯，不留下来自上一次的陈旧位置。

## 考虑过的替代方案

**每次按键都从会话记录推导历史。** 那是持久记录，刷新后仍在，但输入框会为了回答"哪些是纯文本提交"而依赖对话投影（图片、引用、命令 chip 各有自己的节点形态）。由 hub 维护追加列表让这个手势留在输入框内部，并且对来自同一会话其他视图的提交一视同仁。

**单独持久化一份按会话的取回列表。** 它重复会话日志已经拥有的事实，还要在排队消息被删除或编辑时维护自己的失效逻辑。取回是输入便利，不是对话状态，不该进日志。

**改用 `Ctrl+P` / `Alt+↑` 避开与光标移动的冲突。** 冲突是真的，但可以用空草稿与插入点位置这两条规则在本地化解；加修饰键会让这个手势相对于它模仿的工具变得难以发现。

## 影响

在空输入框按 ↑ 会填入上一条提示，继续按往更早走，按 ↓ 回到原处。回溯从不改动草稿的引用、引用块与附件：它只写纯文本，所以一条提到文件的旧提示取回后是可编辑的文本，而不是活的 chip。回溯在同一个会话内换视图后仍然有效（由 hub 持有），会话绑定释放时丢弃。

## 测试

`packages/client/ui-conversation/tests/input-history.client.spec.ts` 驱动真实的输入框外壳：往回走、停在最旧一条、越过最新一条后恢复草稿、已有草稿时不开始回溯、用户编辑后终止回溯，以及提交时记录草稿并跳过空白提交。`packages/client/ui-conversation/tests/keymap-routing.client.spec.tsx` 在 DOM 边界覆盖这个手势：↑/↓ 会进入回溯，带修饰键的方向键与菜单认领会拦截它。
