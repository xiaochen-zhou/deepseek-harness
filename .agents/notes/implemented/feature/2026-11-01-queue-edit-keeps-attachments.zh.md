# Agent Note: 编辑排队消息时保留其附件

Status: implemented

[English](2026-11-01-queue-edit-keeps-attachments.md) | 中文

## 问题

队列面板允许就地编辑待发送的消息，但仅限所有内容块都是文本的情况：携带图片的消息让 `textOf` 返回 `null`，编辑按钮渲染为禁用，并提示不支持非文本内容。宿主侧用 `QUEUE_EDIT_NON_TEXT` 执行同样的规则，而客户端的编辑会替换整个内容列表，因此若为带图消息提交文本，图片会被丢掉。

这让常见场景很别扭：用户排队了"看图"加一张截图，发现错字，只能删除这条消息重新拼一遍——也就必须重新上传图片。

## 决策

编辑只携带文本，它表达的是对消息**文本**的替换，而不是对附件的替换。

- `QueueAction` 的编辑内容仍是 `readonly TextBlock[]`；其 JSDoc 现在说明排队消息已有的图片块保持原位。
- `packages/api/session-controller/src/commands.ts` 中的 `mergeEditedText` 负责合成存储的消息：没有附件块的消息完全等于提交的文本；否则非文本块保持各自位置，提交的文本占据第一个文本位置，其后的文本位置合并进入它，空编辑直接去掉文本，原本没有文本的消息则在末尾追加。
- "内容必须包含非空白文本"的规则现在通过 `hasMessageContent` 作用于合成后的结果，因此纯文本消息仍不能被清空，而带图消息可以只留下图片。仅接受文本载荷的规则与 `QUEUE_EDIT_NON_TEXT` 保留，因为对于自己并不拥有的附件，客户端没有可发送的持久引用。
- `QueueDock` 的 `textOf` 拼接消息的文本块并总是返回字符串，因此每个可变行都启用编辑动作；禁用提示以及八种语言里的 `queue.edit.unsupported` 文案一并移除。

## 考虑过的替代方案

**由客户端回传完整内容列表，含附件。** 队列面板确实持有它渲染缩略图用的持久图片引用，可以原样回传。但这样一来，宿主就要信任客户端为一条本就归宿主所有的消息提供的附件列表：过期或重排的列表会悄悄改变模型收到的图片，而漏发某个块看起来像有意的删除而不是缺陷。此处唯一的用户意图是改文字。

**给编辑动作加一个独立的 `text` 字段。** 它比复用 `content` 更易读，但会与其他所有携带 prompt 的动作在线上形状上分叉，并为一个语义完全相同（文本块本就是编辑唯一允许携带的块类型）的字段引入迁移。

**维持不支持，让用户重新暂存。** 逻辑上正确，但浪费：附件已经持久化并由该消息寻址，重新排队会再次上传存储里已有的字节。

## 影响

编辑带图消息现在只改文字；它携带的图片是逐字节相同的块，因此模型按同样的顺序收到同样的附件。没有说明文字的图片消息可以新增文字，带图消息也可以丢掉全部文字，而纯文本消息仍不允许被清空。删除该条消息仍是丢弃其附件的唯一方式。

合并是宿主的约束而非客户端的约定，因此任何发送 `{ kind: 'edit', content: [text] }` 的 Remote 调用方都得到相同行为。

## 测试

`packages/api/session-controller/tests/commands-queue-attachment.host.spec.ts` 覆盖：文本位于图片之前的消息、纯图片消息先加文字再清空文字、以及图片之后还有第二个文本块时合并到第一个位置。`packages/client/ui-conversation/tests/queue-dock.client.spec.tsx` 覆盖带图行上启用的编辑动作、它提交的纯文本命令，以及每一行排队消息现在都提供可用的编辑动作。
